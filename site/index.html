The problem

New models ship every few weeks. Nobody re-benchmarks forty candidates by hand.

01

You overpay without knowing it. The model you picked eight months ago is still what your app calls — even though three cheaper ones have since matched it.

02

A score moving doesn't tell you why. A prompt edit and an actual model regression look identical on a bare trend line — unless something is tracking what changed.

03

Checking is the part nobody has time for. The only way to find out if something better exists is a person manually re-running the comparison — so it just doesn't happen.

How it works

Discovery and evaluation run automatically. Deployment doesn't.

Everything up to a decision happens on its own, on whatever schedule you choose. The moment your application's actual behavior would change, it stops and asks a person.

Why it's built this way

Six decisions that aren't the obvious default

Per feature, not per model

Each LLM call site gets its own test cases, its own rubric, its own approved model. No global leaderboard pretending one model wins everything.

Proof, not just scores

Every score comes with the candidate's real answer and the judge's stated reasoning, saved with a timestamp — not a number you have to trust blind.

Two human gates, not one

resolve() keeps returning the old model until a human approves. Patching real source code is a second, separate confirmation.

Real cost, latency & validity

Priced against the exact host that was actually called, not a catalogue estimate — plus whether a model needed a retry to produce usable JSON at all.

Multi-provider, for real

OpenRouter, Groq, Fireworks, and OpenAI — each candidate is called through the exact platform it was discovered on, not silently rerouted.

Self-hosted, flat files

No database, no signup, no data leaving your machine. State is JSON and YAML you can read, diff, and commit.

What's next

Benchmarking full agents, not just single calls

Everything above benchmarks one call: one prompt in, one judged answer out. An agent is a loop — it can call a tool, read the result, call the model again, and keep going before it produces a final answer. That needs a different kind of run, not a config flag.

planned, not shipped yet

The sandbox runs the whole loop. One test case means the agent's full sequence of tool calls, not one request — then the judge scores the final answer.

planned, not shipped yet

Checks on the trace, not just the reply. Did it call the right tool? Stop within a reasonable number of steps? That's a different kind of assertion than checking one JSON response.

mostly already there

Cost and latency already generalize. They're summed per call today — an agent run just means summing across every call the loop makes instead of one.

Quickstart

Five minutes to your first leaderboard

Everything runs locally. The only command that spends anything is run — and it shows the cost and asks first.

1

Install & configure

Clone the repo, create a venv, set one API key.

2

Write a use case

Or copy the example under examples/.

3

Run the bench

See the exact candidate list and cost before anything is spent.

4

Approve, from the CLI or the dashboard

The only action that changes what your app receives.

# 1. Install
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Configure
cp .env.example .env
# set OPENROUTER_API_KEY, or add it later
# from the dashboard

# 3. Write a use case
python -m modelcicd.cli init \
  --out feature.yaml

# 4. Free preview — no model calls yet
python -m modelcicd.cli shortlist \
  --use-case feature.yaml

# 5. Run the bench — shows cost, asks first
python -m modelcicd.cli run \
  --use-case feature.yaml

# 6. Approve, or open the dashboard
python -m modelcicd.cli approve \
  --use-case feature.yaml
python -m modelcicd.cli ui

Stop re-checking the model market by hand.

Free, self-hosted, and the whole integration surface is one function call. Everything else in the repo exists to answer one question well.
